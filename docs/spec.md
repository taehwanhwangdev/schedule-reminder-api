# Spec — 일정 알림 API

> 각 절은 "한 줄 요약 → 그림·예시 → 규칙과 이유 → 테스트" 순서로 쓴다.
> 이 문서가 설계의 유일한 기준이다. 구현·테스트가 이 문서와 다르면 문서를 먼저 고치고 나서 코드를 바꾼다.

---

## 0. 한눈에 보기

### 무엇을 하나

사용자가 "언제(현지 시각 + 시간대), 몇 분 전에 알릴지"를 등록하면, 그 시각에 Slack으로 알림을 1번 보낸다.

### 전체 흐름

```
[등록 API] 현지 시각 → UTC 변환 → 일정 저장 + 알림 1건(PENDING) 저장
                                              │
[스케줄러, 1분마다] 도래한 알림 조회 → 선점(PROCESSING) → Slack 발송 → SENT
                                              │
[조회 API] 일정 + 알림 상태 확인     [삭제 API] 알림 취소 → 일정 삭제
```

### 핵심 결정 5줄

1. 시각은 UTC로 저장하고, 시간대는 이름(America/New_York)으로 받는다
2. DST로 사라진 시각은 뒤로 밀고, 두 번 있는 시각은 먼저 오는 쪽을 쓴다
3. 보내기 전에 선점해서 동시 실행에 의한 중복을 막는다
4. "정확히 1회"는 불가능하므로 "최소 1회"를 보장하고, 중복 가능 구간을 좁힌다
5. 스케줄러는 하한 없이 "지금까지 도래한 것 전부"를 조회해 누락을 막는다

### 용어

| 용어          | 뜻                                                                                            |
| ------------- | --------------------------------------------------------------------------------------------- |
| UTC           | 시간대·DST가 없는 기준 시각. 저장과 비교는 모두 UTC로 한다                                    |
| IANA 시간대   | `America/New_York` 같은 이름. 오프셋뿐 아니라 "언제 DST가 시작·종료되는지" 규칙 전체를 담는다 |
| 오프셋        | 그 순간 UTC와의 차이(예: `-05:00`). 계절마다 바뀐다                                           |
| DST           | 서머타임. Spring forward(봄에 시작, 시계를 앞으로), Fall back(가을에 종료, 시계를 뒤로)       |
| notifyAt      | 알림을 보낼 시각(UTC)                                                                         |
| 선점          | "PENDING일 때만 PROCESSING으로 바꿔라"는 조건부 쓰기. 한 실행만 성공한다                      |
| lease         | 선점 유효 시간(5분). 지나면 다른 실행이 다시 선점할 수 있다                                   |
| leaseOwner    | 선점한 실행의 ID. 결과를 기록할 때 "선점한 게 나일 때만"이라는 조건으로 쓴다                  |
| 허용 지연     | 30분. 이보다 늦어진 알림은 보내지 않고 EXPIRED로 기록한다                                     |
| GSI           | 같은 데이터를 다른 기준(여기서는 보낼 시각 순서)으로 다시 정리한 색인                         |
| 희소 인덱스   | 특정 속성이 있는 항목만 들어가는 GSI. 발송 대기 중인 알림만 담는다                            |
| at-least-once | 최소 1회 발송. 누락은 막고, 드물게 중복을 허용한다                                            |

## 1. 시간 계산

### 한 줄 요약

현지 시각과 시간대 이름을 받아 서버에서 UTC로 바꿔 저장하고, 알림 시각은 UTC에서 N분을 빼서 구한다.

### 흐름

```
입력: "2026-03-08T02:30" + "America/New_York"   (오프셋 없음)
  ↓ 시간대 규칙으로 계산
저장: startsAtUtc = "2026-03-08T07:30:00.000Z"   + 원본(startsAtLocal, timeZone)
  ↓
응답: resolvedLocal = "2026-03-08T03:30-04:00"   (실제로 이렇게 해석했다고 알려줌)
  ↓
알림: notifyAt = startsAtUtc − remindBeforeMinutes
```

### 규칙과 이유

| 규칙                                            | 이유                                                                            |
| ----------------------------------------------- | ------------------------------------------------------------------------------- |
| 입력은 오프셋 없는 현지 시각 + IANA 시간대 이름 | 사람은 현지 시각으로 입력한다. 계산은 서버 한 곳에서만 한다                     |
| 오프셋이 붙은 시각, 유효하지 않은 시간대는 400  | 클라이언트가 이미 계산한 값을 받으면 계산하는 곳이 둘이 되어 틀릴 곳이 늘어난다 |
| 시간대는 `-05:00`이 아니라 이름으로 저장        | 오프셋을 고정하면 계절이 다른 일정이 1시간씩 틀린다(아래 예시)                  |
| UTC로 저장하고 원본도 함께 저장                 | 스케줄러 비교 기준을 하나로 만들고, 사용자가 무엇을 입력했는지 남긴다           |
| 등록 응답에 해석된 현지 시각·오프셋 포함        | 시각이 보정됐으면 클라이언트가 알 수 있게 한다                                  |

오프셋을 고정하면 생기는 문제:
| 일정(뉴욕 현지 09:00) | `America/New_York` | `-05:00` 고정 |
| --- | --- | --- |
| 1/15 (겨울, -05:00) | 14:00Z ✅ | 14:00Z ✅ |
| 7/1 (여름, -04:00) | 13:00Z ✅ | 14:00Z ❌ 1시간 늦게 알림 |

### DST 두 경우

**봄: DST 시작 (2026-03-08, 뉴욕)** — 02:00이 되면 시계를 03:00으로 넘긴다. 02:00~02:59는 존재하지 않는다.

```
01:59 EST → 03:00 EDT        (02:30은 벽시계에 안 나타남)
```

- 규칙: 전환 전 오프셋(EST, -5)으로 해석한다 → 02:30 EST = 07:30Z = 벽시계로 03:30
- 이유: 사용자는 "2시 반쯤"을 의도했을 테니, 에러보다 1시간 밀어 주는 쪽이 자연스럽다. 거절(400)도 맞는 선택지지만 입력 편의를 택했고, 대신 응답으로 해석 결과를 돌려준다

**가을: DST 종료 (2026-11-01, 뉴욕)** — 02:00(EDT)이 되면 시계를 01:00으로 되돌린다. 01:00~01:59가 두 번 지나간다.

```
01:30 EDT(-4) = 05:30Z   ← 첫 번째 (채택)
01:30 EST(-5) = 06:30Z   ← 두 번째
```

- 규칙: 먼저 오는 쪽(전환 전 오프셋)을 쓴다
- 이유: 알림은 늦는 것보다 이른 것이 안전하다. 나중 쪽을 고르면, 첫 번째 01:30을 의도한 사용자는 1시간 늦게 받는다
- 주의: 01:30이 두 번 지나가도 중복 발송은 생기지 않는다. 등록할 때 UTC 한 순간으로 한 번만 변환해 저장하기 때문이다

두 규칙을 합친 동작은 Temporal의 기본값(`compatible`)과 같다.

### 알림 시각 계산

- `notifyAt = startsAtUtc − remindBeforeMinutes`. 뺄셈은 UTC에서 한다
- 이유: "60분 전"이 DST 날에도 정확히 60분 전이어야 한다. 현지 시계로 빼면 DST 날 "1시간 전"이 2시간 전이나 0시간 전이 된다
- 결과: DST를 넘는 긴 알림은 현지 시각이 1시간 달라 보인다(의도된 동작, README에 명시)

```
일정: 3/8 10:00 EDT = 14:00Z
1440분 전 = 3/7 14:00Z = 현지 3/7 09:00 EST   ← "전날 10시"가 아니라 "전날 9시"
설명: 정확히 24시간 전인데, 그 사이 서머타임이 시작돼 시계가 1시간 앞당겨졌다
```

### 검증과 판정

| 상황                                                  | 처리                                                                                                   |
| ----------------------------------------------------- | ------------------------------------------------------------------------------------------------------ |
| 일정 시각이 이미 지남                                 | 400                                                                                                    |
| 알림 시각만 이미 지남(예: 일정 30분 뒤, 60분 전 알림) | 일정은 등록, 알림은 만들지 않음(`notifyAt: null`). 등록 직후 "1시간 전입니다"라는 틀린 메시지를 막는다 |
| 발송 대상 판정                                        | `notifyAt <= now`(같으면 포함). `<`와 `<=`는 AI가 조용히 틀리기 쉬워 T9로 고정한다                     |

### 테스트 (단위)

| #   | 입력                                         | 기대값                              | 확인하는 것     |
| --- | -------------------------------------------- | ----------------------------------- | --------------- |
| T1  | Asia/Seoul 2026-11-20T10:00, 60분 전         | 일정 2026-11-20T01:00Z, 알림 00:00Z | 기본 변환       |
| T2  | America/New_York 2026-07-01T09:00            | 2026-07-01T13:00Z                   | 여름 오프셋(-4) |
| T3  | America/New_York 2026-03-08T02:30            | 2026-03-08T07:30Z, 응답 03:30-04:00 | 사라진 시각     |
| T4  | America/New_York 2026-11-01T01:30            | 2026-11-01T05:30Z                   | 두 번 있는 시각 |
| T5  | America/New_York 2026-03-08T10:00, 1440분 전 | 2026-03-07T14:00Z(현지 09:00 EST)   | DST를 넘는 알림 |
| T6  | 시간대 "Mars/Base"                           | 400                                 | 시간대 검증     |
| T7  | 일정 시각이 과거                             | 400                                 | 과거 일정       |
| T8  | 일정 30분 뒤, 60분 전                        | 알림 생성 안 함(`notifyAt: null`)   | 지난 알림 시각  |
| T9  | notifyAt == now                              | 발송 대상                           | 경계 포함       |

- DST 전환일과 기대 UTC 값은 사람이 계산한 값이다. 라이브러리 결과와 다르면 테스트를 고치기 전에 원인부터 본다

## 2. 중복·누락

### 한 줄 요약

보내기 전에 선점해서 동시 실행을 막고, 선점한 실행이 죽으면 lease가 끝난 뒤 다시 잡게 하며, 하한 없는 조회로 누락을 막는다.

### 보장 수준: 최소 1회 (정확히 1회가 아닌 이유)

알림을 보낼 때는 "Slack에 보내기"와 "DB에 SENT 기록하기" 두 가지가 일어난다. 서로 다른 시스템이라 둘을 하나로 묶을 수 없고, 둘 사이에는 항상 틈이 있다.

| 순서                      | 틈에서 죽으면                                | 결과 |
| ------------------------- | -------------------------------------------- | ---- |
| 기록 먼저 → 보내기        | 기록은 "보냄"인데 실제로는 안 감             | 누락 |
| 보내기 먼저 → 기록 (채택) | 실제로는 갔는데 기록이 없어 나중에 다시 보냄 | 중복 |

- 알림은 안 오는 것보다 두 번 오는 게 낫다 → 최소 1회를 택한다
- 중복은 "보낸 직후, SENT 기록 전에 죽은 경우"로만 좁힌다
- 받는 쪽이 같은 ID를 한 번만 처리해 주면(멱등 키) 정확히 1회도 가능하지만, Slack 웹훅에는 그 기능이 없다

### 상태 흐름

```
           선점                  발송 성공
PENDING ─────────→ PROCESSING ─────────→ SENT
   │  ↑                 │
   │  └── 발송 실패 ────┤ (시도 3회 미만이면 다시 대기)
   │                    └── 발송 실패, 3회째 → FAILED
   │
   ├── 30분 넘게 늦음 → EXPIRED (보내지 않음)
   └── 일정 삭제 → CANCELED
```

| 상태                               | 뜻                         | 발송 대기 GSI                           |
| ---------------------------------- | -------------------------- | --------------------------------------- |
| PENDING                            | 보낼 차례를 기다림         | 있음                                    |
| PROCESSING                         | 어떤 실행이 잡고 보내는 중 | 있음(lease가 끝나면 다시 잡혀야 하므로) |
| SENT · FAILED · EXPIRED · CANCELED | 끝남                       | 없음(pendingKey 제거)                   |

**PROCESSING이 필요한 이유(초기 설계 결함):** 처음 설계는 PENDING → SENT뿐이었고, 발송 후에 조건부 쓰기를 했다. 두 실행이 겹치면 둘 다 PENDING을 읽고 둘 다 보낸 뒤에야 한쪽 기록이 막혔다. 그래서 발송 전에 PROCESSING으로 선점하는 단계를 넣었다.

### 스케줄러 한 번의 실행 (1분마다)

```
1. GSI 조회: pendingKey = "PENDING" 이고 notifyAt <= now   (50건씩, 남은 시간이 부족하면 다음 실행에 넘김)
2. 건마다(한 건의 실패가 다른 건에 영향을 주지 않음)
   a. notifyAt < now − 30분 → EXPIRED, 로그 (보내지 않음)
   b. 선점: 조건 [status = PENDING] 또는 [status = PROCESSING 이고 leaseUntil < now]
            → status = PROCESSING, leaseUntil = now + 5분, leaseOwner = 내 실행 ID, attempts + 1
            조건 실패 = 다른 실행이 처리 중 → 건너뜀
   c. Slack 발송
   d. 성공 → SENT (조건: leaseOwner = 내 실행 ID)
      실패 → attempts < 3 이면 PENDING 복귀, 아니면 FAILED (같은 조건)
```

### 선점·lease·leaseOwner가 막는 것

| 상황                                       | 일어나는 일                                                             | 사용자가 받는 알림 |
| ------------------------------------------ | ----------------------------------------------------------------------- | ------------------ |
| 두 실행이 동시에 같은 알림을 잡음          | 선점 조건부 쓰기는 항목 단위로 원자적이라 한쪽만 성공, 다른 쪽은 건너뜀 | 1번                |
| 선점 후 발송 **전에** 죽음                 | 5분 뒤 lease 만료 → 다음 실행이 재선점(attempts 2) → 발송               | 1번, 약 5~6분 늦게 |
| 선점 후 발송 **후에** 죽음(SENT 기록 전)   | 5분 뒤 lease 만료 → 다음 실행이 재선점 → 다시 발송                      | 2번(감수하는 중복) |
| lease가 끝난 뒤 이전 실행이 늦게 결과 기록 | leaseOwner 조건 불일치로 거부                                           | 영향 없음          |

- lease(5분)를 Lambda 제한 시간(60초)보다 길게 잡는다: lease가 끝났을 때 이전 실행은 이미 종료돼 있어야 한다
- leaseOwner는 이중 안전장치다: 보통은 lease > 제한 시간으로 충분하지만, 누군가 제한 시간을 늘리는 식으로 설정이 바뀌어도 늦게 끝난 실행이 다른 실행의 결과를 덮어쓰지 못하게 한다

### 누락을 막는 조회

- **하한 없음:** "최근 1분 사이 도래분"처럼 하한을 두면, 스케줄러가 한 번 건너뛸 때 그 사이 알림이 영영 빠진다. 하한이 없으면 멈췄다 돌아와도 밀린 것을 전부 잡는다
- **GSI는 후보 목록, 결정은 기본 테이블:** GSI는 기본 테이블보다 늦게 반영될 수 있다
  - 새 알림이 GSI에 아직 안 보임 → 다음 실행(1분 뒤)에 잡힌다(하한이 없어서 빠지지 않음)
  - 이미 처리된 알림이 GSI에 아직 남아 있음 → 기본 테이블의 선점 조건부 쓰기가 실패해서 건너뛴다
- **허용 지연(30분):** 재가동 시점 기준으로 판정한다

```
멈춤 ────── 2시간 ────── 재가동(now)
            │← 30분 이내 →│
  이 구간 도래분: EXPIRED     이 구간 도래분: 늦게라도 발송
```

- EXPIRED는 알림 상태만 바꾼다. 일정은 남고, GET으로 보면 알림 상태가 EXPIRED다
- 허용 지연(30분, 늦으면 안 보냄)과 lease(5분, 선점 유효 시간)는 다른 개념이다

### 테스트 (통합, DynamoDB Local)

| #   | 상황                                          | 기대값                                      |
| --- | --------------------------------------------- | ------------------------------------------- |
| I1  | 같은 알림을 두 실행이 동시에 처리             | 발송 1회, 한쪽은 선점 실패로 건너뜀         |
| I2  | 선점 후 발송 전에 중단(lease 남음)            | 다른 실행이 건너뜀                          |
| I3  | 선점 후 중단, lease 만료                      | 다음 실행이 재선점해 1회 발송               |
| I4  | lease 만료 후 이전 실행이 늦게 SENT 기록 시도 | leaseOwner 불일치로 거부                    |
| I5  | 3건 중 1건 발송 실패                          | 나머지 2건 SENT, 실패 건 PENDING·attempts 1 |
| I6  | 3회 연속 실패                                 | FAILED, GSI에서 빠짐                        |
| I7  | notifyAt이 31분 지난 PENDING                  | EXPIRED, 발송 안 함                         |
| I8  | 삭제 시 PENDING 알림                          | CANCELED, 이후 발송 안 함                   |

- GSI 반영 지연은 DynamoDB Local에서 재현하기 어렵다 → 판단을 기본 테이블 조건부 쓰기로 하는 설계로 대응하고, README에 한계로 명시한다
- 끝까지 지키는 테스트: I1, I3, I5

## 3. 데이터·API

### 한 줄 요약

일정과 그 알림을 같은 PK에 두어 API는 한 번에 읽고, 스케줄러는 별도 GSI(보낼 시각 순서)로 찾는다.

### 단일 테이블: 우편함 비유

- 테이블은 호수별 우편함이다. PK가 호수, SK가 우편함 안의 우편물 이름이다
- 우편함 `SCHEDULE#abc` 안에 일정 정보(`META`)와 그 일정의 알림(`NOTIF#60`)이 함께 들어 있다
- DynamoDB에는 조인이 없어서, 함께 읽고 함께 지우는 것을 같은 PK에 둔다

| PK             | SK           | 내용                                |
| -------------- | ------------ | ----------------------------------- |
| `SCHEDULE#abc` | `META`       | 일정: 치과 예약, 3/8 02:30, 60분 전 |
| `SCHEDULE#abc` | `NOTIF#60`   | 알림: notifyAt 06:30Z, PENDING      |
| `SCHEDULE#xyz` | `META`       | 일정: 회의, 11/20 10:00, 1440분 전  |
| `SCHEDULE#xyz` | `NOTIF#1440` | 알림: notifyAt 11/19 01:00Z, SENT   |

- 접두어(`SCHEDULE#`, `NOTIF#`)는 종류 표시다. 한 테이블에 여러 종류가 섞여도 키만 보고 구분하고, 서로 겹치지 않게 한다
- SK에 분(`#60`)을 넣는 이유: 지금은 알림이 1개지만, 알림 시점을 여러 개로 되살리면 `NOTIF#1440`, `NOTIF#60`처럼 각각 다른 항목이 된다

### 누가 어디서 읽나

| 누가     | 질문                  | 아는 것     | 어디서 읽나                                            |
| -------- | --------------------- | ----------- | ------------------------------------------------------ |
| API(GET) | "일정 abc 보여줘"     | 일정 ID     | 테이블: `PK = SCHEDULE#abc` Query 1번 → 2개 반환       |
| 스케줄러 | "지금 보낼 알림 전부" | 지금 시각만 | GSI `pending-index`: 보낼 시각 순서로 정리된 배달 명단 |

- 스케줄러는 일정 ID를 모르니 테이블로는 모든 우편함을 열어야 한다(Scan). 그래서 같은 데이터를 시각 순서로 다시 정리한 GSI를 둔다
- GSI `pending-index`: PK `pendingKey`(상수 `"PENDING"`), SK `notifyAt`, 프로젝션 ALL. pendingKey는 PENDING·PROCESSING일 때만 있어서 발송 대기 중인 알림만 들어간다(희소 인덱스)
- 이 GSI는 파티션이 하나라 규모가 커지면 병목이 된다. 이 규모에서는 단순성을 택했고, 커지면 시간 버킷으로 파티션을 나눈다

### 시각 형식은 하나로 고정

- DynamoDB에는 날짜 타입이 없어 시각을 문자열로 저장한다. 문자열은 앞에서부터 한 글자씩 비교한다(사전순)
- 형식이 같으면 사전순 = 시간순이다. 형식이 섞이면 틀어진다

```
A = "2026-03-08T15:30:00+09:00"   (실제 06:30Z)
B = "2026-03-08T07:00:00.000Z"    (07:00Z)
실제로는 A가 이르지만, 문자열 비교는 "15" > "07"이라 A가 늦다고 판단 ❌
→ notifyAt <= now 판정이 틀려 보내야 할 알림을 안 보낸다(에러 없이 조용히)
```

- 규칙: 모든 UTC 시각은 `toISOString()` 형식(`YYYY-MM-DDTHH:mm:ss.sssZ`, 항상 Z와 밀리초)으로만 저장한다
- 숫자(epoch)로 저장해도 되지만, 사람이 읽기 쉬운 ISO 문자열을 택하고 형식을 고정했다

### 일정 항목 (SK = `META`)

| 속성                | 타입   | 설명                                         | 예시                         |
| ------------------- | ------ | -------------------------------------------- | ---------------------------- |
| scheduleId          | string | 일정 ID(UUID). PK에도 쓰지만 응답용으로 저장 | `"3f2a..."`                  |
| title               | string | 일정 제목, 1~100자                           | `"치과 예약"`                |
| startsAtLocal       | string | 입력한 현지 시각(오프셋 없음), 원본 보존     | `"2026-03-08T02:30"`         |
| timeZone            | string | IANA 시간대 이름                             | `"America/New_York"`         |
| startsAtUtc         | string | 변환한 일정 시각(UTC)                        | `"2026-03-08T07:30:00.000Z"` |
| resolvedLocal       | string | 실제로 해석된 현지 시각 + 오프셋             | `"2026-03-08T03:30-04:00"`   |
| remindBeforeMinutes | number | 몇 분 전에 알릴지, 정수 1~10080              | `60`                         |
| createdAt           | string | 생성 시각(UTC)                               | `"2026-11-05T01:00:00.000Z"` |

### 알림 항목 (SK = `NOTIF#<minutes>`)

| 속성        | 타입   | 설명                                                                 | 예시                         |
| ----------- | ------ | -------------------------------------------------------------------- | ---------------------------- |
| notifyAt    | string | 발송 예정 시각(UTC) = startsAtUtc − remindBeforeMinutes. GSI 정렬 키 | `"2026-03-08T06:30:00.000Z"` |
| status      | string | PENDING / PROCESSING / SENT / FAILED / EXPIRED / CANCELED            | `"PENDING"`                  |
| pendingKey  | string | GSI 파티션 키. 값은 `"PENDING"`, PENDING·PROCESSING일 때만 존재      | `"PENDING"`                  |
| attempts    | number | 선점 횟수. 선점할 때마다 +1, 3회를 넘기면 FAILED                     | `1`                          |
| leaseUntil  | string | 선점 만료 시각(UTC) = 선점 시각 + 5분                                | `"2026-03-08T06:35:00.000Z"` |
| leaseOwner  | string | 선점한 실행 ID(Lambda 요청 ID)                                       | `"c1d9..."`                  |
| title       | string | 발송 메시지용 복사본                                                 | `"치과 예약"`                |
| startsAtUtc | string | 발송 메시지용 복사본                                                 | `"2026-03-08T07:30:00.000Z"` |
| timeZone    | string | 발송 메시지에 현지 시각을 표시하기 위한 복사본                       | `"America/New_York"`         |
| updatedAt   | string | 마지막 상태 변경 시각(UTC)                                           | `"2026-03-08T06:30:05.000Z"` |

- 생성 시: status = PENDING, pendingKey = "PENDING", attempts = 0, leaseUntil·leaseOwner 없음
- 복사본을 두는 이유: 스케줄러가 건마다 일정 항목을 다시 읽지 않게 한다. 일정 수정 API가 없어서 원본과 어긋날 일도 없다

### API

| 메서드 | 경로            | 성공                                                               | 실패 |
| ------ | --------------- | ------------------------------------------------------------------ | ---- |
| POST   | /schedules      | 201 `{ scheduleId, startsAtUtc, resolvedLocal, notifyAt \| null }` | 400  |
| GET    | /schedules/{id} | 200 `{ 일정 + 알림 상태 }`                                         | 404  |
| DELETE | /schedules/{id} | 204                                                                | 404  |

- POST 본문: `{ title, startsAtLocal, timeZone, remindBeforeMinutes }`
- 검증(400): 필수값 누락, title 1~100자, 오프셋 포함 시각, 유효하지 않은 시간대, 과거 일정, remindBeforeMinutes 정수 1~10080
- 오류 형식: `{ "error": { "code": "...", "message": "..." } }`
- 목록 조회는 범위 밖(사용자 구분·인증이 필요해진다)

### 삭제 (단순 취소)

| 순서                         | 중간에 실패하면                                                                    |
| ---------------------------- | ---------------------------------------------------------------------------------- |
| 알림 취소 → 일정 삭제 (채택) | 일정이 남아 있으니 다시 삭제 요청하면 된다                                         |
| 일정 삭제 → 알림 취소        | 지워진 일정의 알림이 PENDING으로 남아 발송된다. 일정이 없으니 API로 찾을 수도 없다 |

- 알림 취소는 조건부: PENDING → CANCELED(pendingKey 제거)
- 이미 PROCESSING인 알림은 취소되지 않고 발송될 수 있다(최대 lease 5분)

## 4. 알려진 한계 (README 후보)

- 정확히 1회 발송을 보장하지 않는다(최소 1회, 중복은 발송 후 기록 전에 죽은 경우만)
- 발송 중(PROCESSING)인 알림은 일정을 삭제해도 발송될 수 있다(최대 5분)
- DST를 넘는 긴 알림은 현지 시각이 1시간 달라 보일 수 있다(정확히 N분 전 기준)
- GSI 반영 지연은 로컬에서 재현하지 못했고, 설계로 대응했다
- 발송 대기 GSI는 파티션이 하나라 대규모에서는 병목이 된다
- 목록 조회·인증·알림 시점 여러 개는 범위 밖
